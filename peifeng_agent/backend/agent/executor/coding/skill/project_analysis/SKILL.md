# 理解与设计项目结构（自顶向下）

作用是**先把项目读清楚，再动手**。改动一个自己没读透的项目，代价一定大于读它。

## 一、分析顺序（不许跳层）

| 层 | 看什么 | 怎么看 |
|---|---|---|
| 1. 目录 | 一级目录的名字与职责边界（谁是源码、谁是数据、谁是产物、谁是配置） | `read(targets=[{"path": "."}])` 列条目；不要一开始就递归全量 |
| 2. 入口 | 程序从哪进、注册了什么（`__main__` / `main.py` / `app.py` / console script） | 读入口文件全文（通常不超过 200 行） |
| 3. 模块 | 每个模块的**变化原因**是否单一（一个文件是否承担了两件不相关的事） | 看 import 关系；`read(targets=[{"path": "<目录>", "grep": ".py"}])` |
| 4. 接口 | 模块之间传什么：函数签名、数据结构、约定的字段名/错误码 | `read(grep="def ")` 提取签名，再挑关键函数读实现 |
| 5. 功能 | 一条真实调用链从入口到落点经过哪些函数，中间转换了什么 | 顺着 import 与调用点走一条链，不要求走全部 |

## 二、产出：结构报告（写成 Markdown 落盘）

```markdown
# <项目名> 结构分析

## 目录与职责
| 路径 | 职责 | 备注 |
|---|---|---|

## 入口与调用链
入口：<文件:函数> → … → <落点>

## 模块与依赖方向
- <模块 A> → <模块 B>（单向，无回指）

## 关键接口（签名 + 契约）
- `func(arg: T) -> R`：约定 …

## 发现的问题
1. <问题>：位置 <文件:行>，影响 <…>，建议 <…>
```

**每条结论都要带位置**（文件 + 行号或函数名）。没有位置的结论等于没读。

## 三、反向设计（还没动手、要先定结构时）

1. 先定**边界**：这个项目负责什么、不负责什么（一句话）
2. 再定**变化原因**：哪些东西会一起变？一起变的放同一个模块；不一起变的分开
3. 定**依赖方向**：只允许单向（上层依赖下层），出现环就是设计错了
4. 定**层级深度**：三层以内；超过三层通常是分类没想清
5. 定**产物与运行时数据分离**：生成物、缓存、日志各自独立目录，不混进源码

## 四、四个常见坑

1. **一次读全部**：几百个文件全读一遍既慢又记不住。先目录→入口→一条链。
2. **拿文件名当职责**：`utils.py` / `helpers.py` 往往什么都有，必须点开看内容再判定。
3. **只看定义不看调用**：签名对了但调用方传的字段不对，是最常见的坑；接口要连调用点一起看。
4. **报告写成读后感**：没有位置、没有依赖方向、没有结论，等于没做。
