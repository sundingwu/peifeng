# 修改代码

**最小改动原则**：只改为了达成目标**必须改**的那几行。顺手重构会把"一个 bug"变成"三个 bug"。

## 一、五步流程（顺序不能换）

1. **定位**：找到要改的那几行，产出「文件:行号 + 当前逻辑一句话」。定位靠 `read(grep="关键词")`，不靠猜。
2. **看调用方**：`read(grep="<函数名>")` 找出所有调用点，确认改签名会不会打断别人。**能不改签名就不改**。
3. **小改**：一次只改一个意图。能用 `write(edits=[{oldText, newText}])` 精确替换就不要整体重写文件。
4. **立刻验证**：改完马上跑（`bash python <脚本>`），不要攒一堆改动再一起跑——出错就分不清是哪一处。
5. **回归**：跑一次原本能过的用例/样本，确认没把它改坏。

## 二、四条约束

| 约束 | 说明 |
|---|---|
| 不改公开契约 | 函数名、参数名、返回结构、错误类型尽量保持；必须改就同步所有调用点并在报告里列出 |
| 不动无关代码 | 缩进、命名、import 顺序、注释风格都不在本次改动范围（除非它导致 bug） |
| 保留原行为 | 改 A 需求时发现 B 也有问题：**记下来，不要顺手改** |
| 改动可回退 | 大改前先 `write` 备份一份（或确认有版本控制），报告里说明怎么退 |

## 三、改动报告（写进 content）

```
改动：<文件:行号> — <原来怎样> → <现在怎样>，为什么
影响面：调用该函数的 3 处（已核对，签名未变）
验证：`python test_demo.py` → 退出码 0，输出与改动前一致
未处理（发现了但不在本次范围）：<问题> 在 <文件:行号>
```

## 四、三个高频错误

1. **整体重写代替精确替换**：一个 300 行的文件只改 2 行，却重写全文——很容易丢掉别处的细节。
2. **改完不跑**：语法错误、缩进错误都是"看起来对"的。
3. **顺手优化**：改 bug 时顺手改命名，评审时没人能分清哪部分是为了修 bug。
